# 技术严谨性规范（常驻）

> 进行技术判断、回答技术问题、编写代码时必须遵守本规则，防止 AI 凭"想当然"给出错误或误导性的技术结论。
> 本项目的真实技术栈：Vue 3.5（`<script setup lang="ts">`）、Vuetify 4（Material Design 3）、TypeScript 6、Vite 8、Vue Router 4、Pinia 4、Tailwind CSS 4、date-fns 4、Sass（sass-embedded）。

---

## 1. 来源优先

每个技术判断**必须基于**以下可信来源之一：

- 官方文档（Vue、Vuetify、Vite、TypeScript、date-fns 等官方文档）
- 项目源码（已通过 `read_file`、`search_files` 等工具实际查阅 `src/`）
- 项目已有代码模式（已确认存在的写法，如 `src/utils/request.ts` 的封装）
- 公认最佳实践（业界广泛认可的方案）

### 推断标注

如果某个结论是你基于经验**推断**而非直接验证的，**必须标注 `[推测]`**：

```typescript
// ✅ 正确：标注推测
// [推测] Vuetify 的 v-data-table 可能支持 #item.<name> 具名插槽做单元格自定义渲染，需查阅文档确认
const slotName = `item.${column.key}`;

// ❌ 错误：未标注，伪装成确定结论
// Vuetify 的 v-data-table 支持 item 插槽
```

### 禁止的写法

- ❌ 将未验证的推断作为确定结论输出
- ❌ 凭记忆声称某个 API 存在或不存在
- ❌ 引用不确定的版本号或特性
- ❌ 将其他项目/库的 API（如 Element Plus、win-design）直接套用到本项目的 Vuetify

---

## 2. 边界意识

如果**不确定**某个 API 是否存在、某个行为是否如此，**必须明确说"我不确定"**，**绝不要猜测**。

### 正确做法

```
// ✅ 明确表达不确定性
"我不确定 Vuetify 的 v-dialog 是否支持 persistent 属性，
建议查阅 Vuetify 官方文档确认。"

// ✅ 先验证再回答
// 通过 read_file 工具查阅项目源码或文档后，给出确定结论
```

### 禁止的写法

- ❌ 不确定时仍给出肯定结论
- ❌ 用模糊措辞掩盖不确定性（如"应该是"、"大概"）
- ❌ 将其他 UI 库（Element Plus / Ant Design Vue / win-design 等）的 API 直接套用到 Vuetify

---

## 3. 版本敏感

提到具体版本号时，**必须是有把握的**。本项目 `package.json` 中声明：Vue 3.5.x、Vuetify 4.1.x、TypeScript 6.0.x、Vite 8.1.x、date-fns 4.4.x。

### 版本确定性规则

| 时间范围 | 确定性 | 处理方式 |
|----------|--------|----------|
| 已发布且已验证 | 确定 | 正常引用 |
| 已发布但未验证 | 不确定 | 标注 `[推测]` |
| 近 3 个月内发布 | 基本确定 | 正常引用，但**必须标注具体发布日期** |
| 当前日期之后发布 | 默认不确定 | 必须标注 `[推测]` |

### 禁止的写法

- ❌ 对未验证的版本特性给出确定结论
- ❌ 混淆不同版本的 API 差异
- ❌ 将 beta/experimental 特性当作稳定特性推荐

---

## 4. 可验证

给出代码的同时，**必须给出验证该代码正确性的方法**：

### 验证方式（按优先级）

1. **lint 检查**：`npm run lint` 验证代码质量
2. **类型检查**：`npm run typecheck`（`vue-tsc`）验证 TS 类型正确性
3. **运行验证**：在浏览器或 Node 中实际执行验证

### 禁止的写法

- ❌ 只给代码不给验证方法
- ❌ 验证方法不可操作（如"请自行测试"）
- ❌ 验证方法与代码不匹配

---

## 5. 自我质疑

回答完毕后，**必须从"代码审查者"角度列出回答中可能存在的 2-3 个风险点**。

### 风险点格式

```
### ⚠️ 风险点

1. **[风险类别]**：描述具体风险及可能的影响
2. **[风险类别]**：描述具体风险及可能的影响
3. **[风险类别]**：描述具体风险及可能的影响
```

### 风险类别示例

| 类别 | 说明 |
|------|------|
| 兼容性风险 | API 可能在某些版本不存在 |
| 性能风险 | 方案可能存在性能瓶颈 |
| 类型安全风险 | 类型定义可能不完整 |
| 边界情况风险 | 未处理某些边界情况 |
| 依赖风险 | 依赖的库或 API 可能变更 |
| 项目规范风险 | 可能与本项目现有规范/目录结构冲突 |

- [ ] 不确定的地方是否明确说了"我不确定"
