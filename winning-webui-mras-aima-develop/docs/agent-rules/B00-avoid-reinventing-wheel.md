# 避免重复造轮子规范（按需：架构设计 / 方案输出 / 代码生成时）

> 在架构设计、方案输出及代码生成过程中，**必须严格遵循"避免重复造轮子"的核心原则**，优先评估并采用当前技术生态下成熟的插件、组件或库等第三方技术方案，**杜绝轻易自行实现**。

## 1. 第三方方案优先

当需要实现以下功能时，**必须先搜索和评估第三方方案**：

- 通用功能（日期处理、数据校验、文件上传、图表渲染、富文本编辑等）
- UI 组件（表格、表单、弹窗、树形控件、拖拽排序等）
- 基础设施（状态管理、路由、HTTP 请求、WebSocket、国际化等）
- 工具函数（防抖节流、深拷贝、URL 解析、格式转换等）

```typescript
// ❌ 错误：自行实现防抖
function debounce(fn: Function, delay: number) { /* ... */ }
// ✅ 正确：优先用 @vueuse/core 的 useDebounceFn 或 lodash-es/debounce
```

## 2. 方案评估核心指标

筛选第三方技术方案时，**必须深度考察**：

- **开源协议**：MIT / Apache 2.0 / BSD（宽松，商业友好）；LGPL（中等）；GPL / AGPL（严格，商业慎用）；无协议（禁止）。
- **社区活跃度**：GitHub Star（≥1000 优秀，≥5000 成熟）、npm 周下载量（≥10k 活跃）、近 3 个月提交、Issue 处理速度、近 6 个月有发布。
- **维护者背景**：知名开源贡献者 / 科技公司（Google、Meta、Vercel 等）/ 团队规模 / 资金赞助。
- **社区口碑**：GitHub Issues / Discussions、Stack Overflow、技术社区（掘金、知乎等）。
- **技术质量**：TypeScript 支持、文档质量、测试覆盖率、Bundle Size、兼容性。

## 3. 方案评估流程

1. 需求分析（功能、技术约束、性能要求）
2. 方案搜索（npm、GitHub、awesome 列表、官方生态）
3. 综合评估（按上述指标输出评分表）
4. 输出**最优方案**（1 个，附推荐理由）+ **备选方案**（1-3 个，对比差异）
5. **与用户确认最优方案后再实施**

## 4. 自行实现的例外情况

以下情况**可以**自行实现，但必须在方案中**明确说明理由**：

| 场景 | 说明 |
|------|------|
| 无合适的第三方方案 | 经过充分搜索，确认没有满足需求的成熟方案 |
| 第三方方案存在严重缺陷 | 安全漏洞、长期未维护、协议不合规等 |
| 功能极度定制化 | 需求高度定制，第三方无法满足且改造成本过高 |
| 包体积严格限制 | 第三方体积过大，且无法按需引入 |
| 学习/演示目的 | 明确为了学习原理或技术演示 |

**自行实现时必须标注**：

```typescript
// ⚠️ 自行实现说明：
// 1. 已搜索的第三方方案：[列出]
// 2. 不采用的原因：[详细说明]
// 3. 自行实现的风险：[维护成本、边界情况等]
```
