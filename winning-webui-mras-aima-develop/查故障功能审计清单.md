# 「查故障」功能 前后端对照审计报告

> 审计对象：当前前端 `winning-webui-mras-aima`（workspace 根目录）
> 对照基准：后端 `winning-winex-mras-aima`、readonly 参考前端 `readonly/winning-webui-mras-aima`
> 审计日期：2026-08-06
> 说明：本文档仅列出问题，不做任何代码修改，待确认后再执行。

---

## 0. 仓库关系与范围

| 仓库 | 角色 | 与「查故障」的关系 |
|---|---|---|
| `winning-webui-mras-aima`（当前） | **被审计对象 / 待修复** | 查故障主流程，位于 `src/views/ChatView/components/diagnosis/` |
| `winning-winex-mras-aima`（后端） | 契约来源（唯一真相） | `DiagnosisCaseController` 提供 `/api/diagnosis/cases` 状态机接口 |
| `readonly/winning-webui-mras-aima`（参考） | 免鉴权参考实现 | 同一产品的较早/完整版，含医院草稿、诊断导出、影子试跑结构化对比 |

**功能定位**：「查故障」= 医疗核心制度指标异常排查。流程为：确认口径 → 三关校验（结构/事件/数值）→ 登记案例 → 案例查因 → 拟定修改方案（候选 SQL）→ 影子试跑 → 保存医院草稿。当前前端通过 `QuickActions.vue` 的「查故障」入口发起，后端在会话消息中写入 `{{diagnosis_case:<caseId>}}` 锚点，`ChatMessage.vue` 正则命中后懒加载 `DiagnosisCaseCard` 渲染。

## 1. 问题清单（按严重度分级）

### A 级 · 确定性硬缺陷（流程可能走不通 / 用户卡死）

#### A1. 缺失 `REVISE_CANDIDATE` 动作 —— 影子试跑失败后无法修订候选 SQL
- **位置**：`src/views/ChatView/components/diagnosis/diagnosis-constants.ts`（第 9-24 行，仅 13 个动作）；`DiagnosisActionBar.vue` 的 `buildActions`（SHADOW_TRIAL 步骤第 71-74 行仅提供 `RUN_SHADOW_TRIAL`）
- **现象**：后端 `ActionRequest.action` 接受 **14** 个动作（含 `REVISE_CANDIDATE`，见后端 `DiagnosisCaseController`），而前端常量白名单只有 13 个，且动作矩阵里没有任何步骤提供「修订候选」按钮。readonly 参考实现也包含 `REVISE_CANDIDATE`。
- **影响**：当影子试跑失败 / 需回改候选 SQL 时（`SHADOW_FAILED` / `CANDIDATE_FAILED` 等状态），前端**没有任何按钮**可提交 `REVISE_CANDIDATE`，流程直接卡死，用户无法回到 CHANGE_PROPOSAL 修改。
- **建议**：在 `DIAGNOSIS_ACTION` 补 `REVISE_CANDIDATE`，并在 `DiagnosisActionBar` 的 SHADOW_TRIAL（及候选失败相关步骤）下增加「修订候选 SQL」按钮，触发 `DiagnosisActionForm` 的 candidate 表单。

#### A2. `CONFIRM_CALIBER` 后三关可能永不自动跑（需立即与后端确认）
- **位置**：`stores/diagnosis.ts` 的 `advanceGates`（第 110-126 行）；`DiagnosisCaseCard.handleSubmit`（第 89-96 行）
- **现象**：提交 `CONFIRM_CALIBER` 后会调用 `advanceGates`。但 `advanceGates` 先 `currentGateNumber(currentStep)`，**若 `currentStep` 不是 `GATE_*` 步骤则返回 0 并立即退出**。也就是说：如果后端在 `CONFIRM_CALIBER` 之后**没有**把 `currentStep` 推进到 `GATE_1_SCHEMA`，则 `advanceGates` 一进函数就 return，三关**永远不会自动跑**；而 `CALIBER_CONFIRMATION` 步骤下 `buildActions` 只返回「确认冻结口径」一个按钮（已点过），用户**无任何后续入口** → 流程卡死。
- **影响**：高危。取决于后端状态推进行为，要么正常、要么整条排查链路在第一步后就卡死。
- **建议**：① 立即与后端确认 `CONFIRM_CALIBER` 返回快照的 `currentStep`；② 对齐 readonly 做法：把推进循环（`advanceGates` 等价物）**挂在 `CONFIRM_CALIBER` 后端响应返回后**直接调用（而非独立时机），用 `for(;;)` 每轮重读 `currentStep` 并显式发 `RUN_GATE {gate}`；③ **必须加迭代上限 + "currentStep 实际变化"校验**，规避 readonly 循环无上限导致的潜在无限重跑同一关风险；④ 任一关 `status === 'BLOCKED'` 即停止，等待用户"修复后重跑"。

#### A3. ~~`profileId = ruleId` 硬编码，未暴露 profile 选择~~ —— ✅ 已确认：属设计意图，非缺陷（2026-08-06 用户确认）
- **位置**：`src/views/ChatView/components/QuickActions.vue`（第 159-160 行 `const ruleId = selectedRuleIds.value[0]; const profileId = ruleId;`）
- **用户确认**：`profileId` 就是 `ruleId`，即用户手动选择的指标；不必暴露独立的 profile 选择。
- **入口已实现正确的单选 / 多选区分**：`QUICK_ACTION_CARDS` 中 `TROUBLESHOOT` 卡片 `multipleRule: false`（第 37 行）、`CALCULATE` 卡片 `multipleRule: true`（第 26 行）；`v-autocomplete` 的 `:multiple` 绑定 `activeCard?.multipleRule`。因此 **查故障 = 指标单选、算指标 = 指标多选**，与业务规则一致，`ruleModel` computed（第 92-104 行）已正确处理两种形态下的 modelValue。
- **结论**：本条不构成缺陷，从 A 级硬缺陷清单移除。原文档担心的「profile 带 `_NNN` 后缀、需用户选 profile」场景经确认不适用。

#### A4. 诊断报告导出完全未实现（按钮已渲染但点击无反应）
- **位置**：`src/views/ChatView/components/ChatMessage.vue`（导出按钮 第 197-215 行；`handleExportAction` 第 93-96 行是空 TODO 桩）
- **现象**：消息正文中解析出的 `diagnosis_export` / `detail_export` / `upload_comparison_export` 标记会渲染「导出诊断报告 / 导出明细 / 导出对比」按钮，但 `handleExportAction` 仅为 `// TODO: 根据 marker.type 调用对应导出接口`，点击无任何效果。
- **影响**：用户点「导出诊断报告」毫无反应，体验断层。后端实际提供 `POST /api/diagnosis-reports/{reportId}/exports`（readonly 已实现 `createDiagnosisReportExport`）。
- **建议**：按 marker.type 接入对应导出接口（诊断报告走 `diagnosis-reports`，明细走 `sql-runs`/`indicator-exports`），并用 `window.confirm` 做患者级明细二次确认（readonly 已采用）。

### B 级 · 与后端契约未对齐 / 错误处理缺失

#### B1. 明细接口 409 语义未分支处理
- **位置**：`services/diagnosis.ts` 的 `getDiagnosisDetails`（第 94-110 行，`parseApiError` 仅提取文本）；`DiagnosisDetailDialog.vue`
- **现象**：后端明细接口在「未先跑基础校验（缺 overviewSqlHash）」时返回 `409 DIAGNOSIS_DETAIL_CONTEXT_MISSING`，在「知识库口径变更」时返回 `409 DIAGNOSIS_DETAIL_CONTRACT_CHANGED`（`{detail:{code,message}}`）。前端只 `throw new Error(await parseApiError(res))`，弹通用「加载明细失败」，不引导用户先确认口径或重跑。
- **建议**：对 `res.status === 409` 识别 `code`，给出针对性文案（如「请先确认口径并跑通第 2 关」/「口径已变更，请重跑基础校验」），必要时引导用户回到对应步骤。

#### B2. `request()` 无超时 / 重试 / 取消
- **位置**：`src/utils/request.ts`（第 71-101 行，第 99 行注释 `// 待优化: 可统一错误处理、响应结构处理`）
- **现象**：`request()` 仅做 `fetch` + 401 拦截，无 `AbortController`、无超时、无重试。诊断动作（提交动作、拉明细）均为同步 REST，后端执行 SQL 可能较慢；一旦挂起，前端**无限等待**，且 `submittingCaseIds` 提交锁在响应返回前不释放，按钮一直 disabled 无法重试。
- **建议**：为诊断类请求增加超时（如 `AbortController` + 30s）与可重试机制；提交失败时及时释放 `submittingCaseIds`，并提供「重试」入口。

#### B3. 明细缓存永不过期，存在陈旧数据风险
- **位置**：`stores/diagnosis.ts` 的 `loadDetails`（第 85-95 行，key=`${caseId}:${group}:${page}:${pageSize}` 写入后不再失效）
- **现象**：后端明细随排查步骤推进而变化，且存在 30 分钟缓存与 409 合约变更机制；前端缓存**永不失效、无版本/etag 校验**，再次打开可能展示陈旧明细。
- **建议**：至少在同一 caseId 的快照被 `submitAction` 整体替换时清空其 `detailsCache`；或按 `overviewSqlHash` 做缓存失效判断。

#### B4. 成功/错误响应结构不一致，前端需显式约定容错
- **位置**：`services/diagnosis.ts`（直接 `res.json()`）；`parseApiError`（第 23-40 行）
- **现象**：后端**成功直接返回裸快照**（无 `Result<T>` / 无 `ResponseBodyAdvice`），失败为 `{"detail":"..."}` 或 `{"detail":{"code","message"}}`（领域异常才带嵌套 code；校验类异常只返回 `{"detail":"..."}`）。前端 `parseApiError` 已覆盖文本/code/message，但前端**不应假设存在 `{code,data,msg}` 信封**。
- **建议**：在 `services/diagnosis.ts` 顶部注释明确「成功无信封、错误两种形态」的契约；补充对 422（参数校验）、400 的差异化提示。

#### B5. `modelId` 回显可能与用户选择不一致
- **位置**：`types/diagnosis.ts` 的 `DiagnosisCaseSnapshot.modelId`；`QuickActions.vue`（第 169 行取 `currentModelId`）
- **现象**：后端 `getDiagnosisCase` 的 `withExecutableDataFlow` 会把 `aliyun-qwen-plus` **强制改写为 `aliyun-qwen-distill-7b`** 再返回。若前端回显快照里的 `modelId`，用户会看到与所选不同的模型。
- **建议**：前端展示模型时以用户选择/请求值为准，或对后端改写做映射说明；避免直接用快照 `modelId` 当作「用户所选」回显。

#### B6. `releaseResult` 恒为空，前端不应展示「已发布」
- **位置**：后端 `DiagnosisCaseSnapshot.releaseResult` 流程中始终为 `{}`（注释明确「不是正式发布」）；当前 `DiagnosisCaseCard.conclusionSections`（第 66-75 行）**未**包含 `releaseResult`，已规避。
- **现象 / 建议**：维持现状即可，但需在代码注释/Review 中确认**没有任何位置**把 `releaseResult` 渲染为「已发布版本」，以免误导。

### C 级 · 功能完整度缺失（对比 readonly 参考实现）

#### C1. 候选 SQL / 影子试跑以原始 JSON 渲染，缺少结构化对比
- **位置**：`DiagnosisCaseCard.vue` 的 `conclusionSections`（第 66-75 行）+ 模板 `pretty()`（第 77-83 行、201-209 行 `<pre>`）
- **现象**：最核心的「给出修改方案 + 可追溯验证」环节（candidateSql / shadowTrial / draftResult）被直接 `JSON.stringify` 塞进 `<pre>` 原文展示。readonly 参考实现将这些渲染为结构化对比：**抽取数据变化**（中间表总记录数 / 去重业务编号 / 减少 / 新增）、**最终指标结果变化**（分子/分母/结果值）、**案例编号验收**（前后记录数是否符合预期）。
- **影响**：可读性极差，等于把排查成果做成调试输出，是当前体验最差的环节。
- **建议**：为 `candidateSql`（originalSql / candidateSql / diffSummary / validation）、`shadowTrial`（originalResult / candidateResult / recordSetDiff / caseValidation / passed / message）设计结构化卡片；`draftResult` 展示保存状态与草稿 ID。

#### C2. 无「医院草稿」查看 / 导出入口
- **位置**：`services/diagnosis.ts`（仅 4 个函数，无 hospital-drafts / diagnosis-reports）；无对应页面
- **现象**：前端动作矩阵包含 `SAVE_HOSPITAL_DRAFT` 与 `REVALIDATE_HOSPITAL_DRAFT`，但提交后用户**看不到草稿、无法导出/回收**。后端提供 `GET /api/diagnosis/hospital-drafts`、`/hospital-drafts/{draftId}`、`/hospital-drafts/export/package`（readonly 的 `KnowledgeReviewView` 即对应此能力）。
- **影响**：「保存医院草稿」成为死胡同——用户保存后无法查看、复核、导出或回收。
- **建议**：新增医院草稿列表/详情/导出能力（可作为抽屉或独立页面），打通 SAVE → 查看 → 复核 → 导出闭环。

#### C3. 缺 SQL 自动改写能力分级护栏（安全风险）
- **位置**：`DiagnosisActionForm.vue`（`candidate` 表单，当前仅组装 type/layer/sql/requirements）
- **现象**：readonly 的 `unsupportedCapabilities` 对 JOIN / 子查询 / 窗口函数 / 去重 / 聚合 / 集合 / CASE **主动停止自动改写并索要完整候选 SELECT**，仅自动处理「当前抽取 SQL 已有字段的筛选条件」。后端 `buildCandidateForTrial` 优先用 `SafeSqlPredicatePatcher` 改 SQL，失败抛 `CANDIDATE_PATCH_UNSUPPORTED`，模型不允许重写整段 SQL。
- **影响**：若前端不分级直接把用户 SQL 提交，复杂 SQL 会被后端拒绝或回退到确定性白名单，体验差且易踩坑。
- **建议**：前端在 candidate 表单对 SQL 做静态分析，复杂结构提示「请提供完整候选 SELECT」，并复用后端的 `generationMethod` / `rawSqlNotice` 字段向用户解释。

#### C4. 无 SSE 断线 / 会话切换容错（锚点消息竞态）
- **位置**：`QuickActions.startTroubleshooting`（第 187 行创建案例后立即 `loadSessionMessages` 一次）；`stores/chat.ts` 的 SSE 处理
- **现象**：创建案例后仅 `loadSessionMessages` 一次以拉取后端写入的 `{{diagnosis_case:...}}` 锚点消息。若后端异步写入（或写入晚于本次重载），锚点消息拉不到，排查卡片不出现。readonly 用 `waitForPersistedTurn` 轮询落库 + 会话切换后台挂接，避免「切走会话结果丢失」。
- **建议**：创建案例后，若重载未命中锚点消息，做有限次轮询或订阅 SSE 等待 `diagnosis_case` 标记出现；会话切换时保持后台消息挂接（可参考 readonly 的 `activeRunMessages` 机制）。

### D 级 · 健壮性 / 类型安全 / 边界

#### D1. `DiagnosisStepTimeline` 对未知 `currentStep` 静默全部 pending
- **位置**：`DiagnosisStepTimeline.vue`（未知步骤 `activeIndex = -1`）
- **现象**：后端返回非预期 `currentStep` 时，时间线不报错也不高亮，掩盖契约不一致。
- **建议**：对未识别步骤给出显式「未知步骤」提示（如红色 chip），便于发现前后端步骤枚举漂移。

#### D2. `advanceGates` 循环上限 `guard < 5` 静默终止
- **位置**：`stores/diagnosis.ts`（第 113 行）
- **现象**：当前仅 3 关，安全；但若后端状态机扩展，5 次上限可能提前终止连跑且无任何告警。
- **建议**：上限改为「关卡数 + 余量」或基于 `DIAGNOSIS_STEP_ORDER` 动态计算，并在提前退出时 console.warn。

#### D3. 动作参数类型为 `string`，未收窄到枚举
- **位置**：`services/diagnosis.ts` 的 `submitDiagnosisAction(action: string, ...)`；`DiagnosisCaseCard.handleSubmit` / `DiagnosisActionBar` emit 亦为 `string`
- **现象**：`DIAGNOSIS_ACTION` 白名单仅用于「推导按钮」，提交时 `action` 仍是 `string`，误传非法 action 只能在运行时被后端 `DIAGNOSIS_STEP_ORDER_VIOLATION` 拒绝。
- **建议**：将 `action` 类型收窄为 `keyof typeof DIAGNOSIS_ACTION`（配合 A1 补全枚举），把错误挡在编译期。

#### D4. `isDetailAvailable` 依赖可选字段 `overviewSqlHash`
- **位置**：`stores/diagnosis.ts`（第 133-141 行）；`DiagnosisCaseCard`（第 54、187 行）
- **现象**：明细入口可用性依赖 `caseExpectedClassification.overviewSqlHash`（类型 `Record<string,unknown>` 的可选字段）。字段缺失/改名时，按钮永久 disabled 且无任何提示，排查困难。
- **建议**：字段缺失时给出 tooltip/提示「口径未冻结，无法查看明细」；对该可选字段做显式存在性断言与容错。

3. **影子试跑对比 UI 的精细度要求？**（见 C1）
   - 当前前端：candidateSql / shadowTrial / draftResult 直接 `JSON.stringify` 塞 `<pre>` 原文（可读性极差）。
   - **readonly 参考实现已结构化三层对比**（`src/components/DiagnosisCasePanel.vue`）：
     - *第一层 抽取数据变化*（`extractionComparisonRows:122-152`，仅 `SOURCE_EXTRACT` 层显示）：中间表总记录数（formalRows vs shadowRows）、去重业务编号数（originalCount vs candidateCount）、候选抽取减少（removedCount `-N`）、新增（addedCount `+N`）——数据来自 `shadowTrial.recordSetDiff`。
     - *第二层 最终指标结果变化*（`resultComparisonRows:78-99`）：分子 / 分母 / 结果值 / 执行状态四行对比（`originalResult` vs `candidateResult`，缺失回退 `candidateSql.baselineResult`）。
     - *第三层 案例编号验收*（`caseValidationRows:153-170`）：案例编号 / 正式记录数 / 候选记录数 / 变化 / 预期 / 验收（是否符合预期），来自 `caseValidation.baselineCounts` 与 `candidateCounts`。
     - JSON 原文仅保留在可折叠 `<details class="diagnosis-technical">`「技术对账明细」中（`:809-817`），面向实施排查，不是主视图。
   - **判定建议**：建议直接对齐 readonly 的三层表格 + 状态徽章（`data-state`）渲染；若工期紧，可先做第一/二层基础结构化，第三层（案例验收）与折叠 JSON 作为后续增强。
4. **CONFIRM_CALIBER 后 currentStep 的推进行为**（见 A2）
   - 当前前端风险：`stores/diagnosis.ts` 的 `advanceGates` 在 `CONFIRM_CALIBER` 后调用，但先 `currentGateNumber(currentStep)`，若后端没把 `currentStep` 推进到 `GATE_1_SCHEMA` 就立即 return → 三关永不自动跑（调用时机型卡死）。
   - **readonly 参考实现**（`AgentChatView.vue:216-229` `advanceDiagnosisGates`）：在 `CONFIRM_CALIBER` **后端响应返回后立即**调用（而非独立时机），用 `for(;;)` 每轮重读 `currentStep` 并显式发 `RUN_GATE {gate}`，靠"后端逐关推进 currentStep 离开 GATE_*"自然终止；同样有 `if(!gate) return` 守卫——**它规避了"调用时机型卡死"，但仍依赖后端把 currentStep 推到 GATE_1**（若后端不推进，第一轮仍 return，与工作副本同类风险）。
   - **⚠️ readonly 的潜在反向风险（无限循环）**：其循环**无迭代上限、无"currentStep 是否真变化"校验**——若后端某关 PASS 后未推进 `currentStep`，下一轮 `gate` 仍为同一关且非 BLOCKED，会无限重跑同一关。readonly 仅靠后端契约规避，未做前端兜底。
   - **判定建议**：修复时除对齐 readonly「把推进循环挂到 CONFIRM_CALIBER 响应」外，还应**加迭代上限 + currentStep 实际变化校验**，规避 readonly 的潜在无限循环；同时仍需与后端确认 currentStep 推进行为（决定 A2 是否真卡死）。

## 5. 待决策项与建议（汇总）

> 第 2 节已给出 readonly 对照，本节把"需要你拍板的范围/深度"与"我的建议"单独拎出来，便于你一次性定调。

### 决策 1 · 医院草稿查看/导出 + 诊断报告导出 是否纳入本期（C2 / A4）
- **背景**：当前前端这两块要么是空 TODO 桩（A4 三个导出按钮点了没反应），要么是死胡同（C2 保存草稿后看不到、无法导出）。readonly 有完整闭环（`/knowledge-review` 路由 + 真实导出下载）。
- **选项**：
  - **A. 全做**：移植 readonly 的 `KnowledgeReviewView`（草稿列表/详情/回收 ZIP）+ 实装导出按钮。打通"排查 → 方案 → 保存草稿 → 导出"完整价值链路，但工作量最大，且引入一个独立路由/页面。
  - **B. 只做导出（A4）**：实现诊断报告/明细/对比的真实导出（参照 readonly `exportDiagnosis`：标记解析 + 权限门控 + `window.confirm` 二次确认 + blob 下载）；草稿查看（C2）本期暂不做，但 `SAVE_HOSPITAL_DRAFT` 后至少回显 `draftResult.draftId` 与状态。
  - **C. 最小处理**：本期不实现，仅把 A4 空按钮**隐藏/禁用**（避免"点了没反应"），C2 维持现状并补 TODO 注释。
- **我的建议：选 B**。理由：① 导出按钮已经在消息流里渲染出来了，用户点击无反应是**最直观的体验断层**，优先修；② readonly 的 `exportDiagnosis` 实现可直接参照（含权限、二次确认、下载），改造成本可控；③ 草稿查看/回收（C2）涉及独立路由与列表页，若当前产品没有"知识库复核"模块规划，强移植一个完整页面可能超出本前端职责——建议先确认产品是否有这块规划，没有则走 C。

### 决策 2 · 影子试跑对比 UI 做到多深（C1）
- **背景**：当前把 candidateSql / shadowTrial / draftResult 直接 `JSON.stringify` 塞 `<pre>`，可读性极差；readonly 是三层结构化对比。
- **选项**：
  - **A. 完整三层**：抽取数据变化（recordSetDiff）+ 最终指标结果变化（originalResult vs candidateResult）+ 案例编号验收（caseValidation），对齐 readonly。

- **我的建议：选 A（完整三层）**。这是查故障"给出可追溯验证方案"的**核心价值点**；readonly 已验证三层数据结构（recordSetDiff / originalResult~candidateResult / caseValidation）可用，移植时只需用 Vuetify 组件渲染即可，**不增加任何后端依赖**，性价比高。

### 决策 3 · 三关自动跑（A2）怎么修
- **背景**：存在"调用时机型卡死"风险，但修复方向明确（对齐 readonly `advanceDiagnosisGates` + 防无限循环），不一定要等后端确认才能动手。
- **选项**：
  - **A. 直接上健壮版修复**：把推进循环挂到 `CONFIRM_CALIBER` 后端响应之后 + 加迭代上限 + `currentStep` 实际变化校验（无论后端是否推进 currentStep，都能安全终止：不卡死、不无限循环）；同时并行动作发后端确认 `currentStep` 推进行为。

## 6. 实施约束（重要 · 移植时务必遵守）

- **readonly 前端仅作参考，不直接照搬 UI / 交互**。readonly 用大量自定义 CSS 类实现对比表格（如 `.diagnosis-compare-table`、`.diagnosis-case-table`、`.diagnosis-case-reconcile`、自定义 `data-state` 属性徽章）。这些**样式与交互是参考基线，移植到当前项目时必须按本项目技术规范重新实现**，不能复制它的 class 与结构。
- **遵循 Vuetify 4 最佳实践 + Material Design 规范**（已核实当前项目为 `vuetify@^4.1.6` + `vue@^3.5`）：
  - 对比表格优先用官方 `v-table` / `v-data-table`，不用自定义 `.xxx-table` div。
  - 状态徽章用 `v-chip` 的语义色（`color="success" | "error" | "warning"`）表达通过/未通过/待定，**替代 readonly 的 `data-state` 自定义属性**；数值正负变化（`+N` / `-N`）同样用语义色（success/error）而非手写 class。
  - 原 readonly 的 `<details>「技术对账明细」`折叠区，改用 `v-expansion-panel` / `v-expand-transition` 实现。
  - 卡片用 `v-card` + Material Design elevation 层级；间距/栅格遵循 8dp 基准；排版用 Vuetify  typography（`text-h6` / `text-body-2` 等）。
  - 加载态用 `v-progress-linear` / `v-progress-circular`，不自定义 spinner。
- **组件 API 以 Vuetify 4 为准**：例如 `v-date-input`、`v-checkbox-btn`、`v-autocomplete` 等已在本项目使用的组件，保持一致的 props/slots 写法；不引入 readonly 可能使用的 Vuetify 3 旧 API。
- 凡是 readonly 里"能用官方组件表达"的部分，一律用官方组件；仅当官方组件确实无法满足（如极特殊的对账表格布局）时，才用 scoped SCSS 补充，并遵循本项目现有 `*.scss` 组织方式（参考现有组件 styles）。
