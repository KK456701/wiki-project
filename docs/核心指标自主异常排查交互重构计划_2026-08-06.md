# 核心指标自主异常排查交互重构计划

> 日期：2026-08-06
> 范围：异常排查的标准模式、自主排查模式、重新抽取场景和真实浏览器验收
> 本文只固化方案，不包含本次代码修改。

## 一、结论

当前自主排查的模型循环已经能够调用 Wiki、运行证据、双库查询、候选 SQL 和影子试跑工具，但前端仍然把它当成“一次性任务卡”展示，导致以下问题：

1. 模型回答一次普通问题后任务进入 `COMPLETED`，没有继续聊天入口。
2. “提供具体案例”被错误等同于“必须输入患者或就诊号”，无法覆盖科室漏数、整体偏高、时间段异常等问题。
3. “医院确认的业务规则”在所有场景下都被强制必填，实际只有修改 SQL 时才需要。
4. 缺少“SQL 没问题，只需要重新同步或重新计算”的独立处理分支。
5. 标准模式和自主模式的渲染条件没有完全隔离，自主模式下面出现标准模式表单和空白消息。
6. 当前把每次分析、工具调用和观察都平铺成同等级卡片，缺少正常对话、阶段性回复和最终结论的主次关系。

推荐将异常排查重构为：

```text
共同前置：异常排查基础校验
              │
              ▼
        选择排查方式
          ├─ 标准模式：结构化范围 + 明确处理动作
          └─ 自主模式：持续对话 + 可折叠执行过程

处理动作最终归入三类：
  A. 原口径重新抽取/重新计算
  B. 修改抽取 SQL
  C. 修改统计 SQL
```

自主模式中，“思考中”不是只有一句笼统摘要。点击后应看到模型专门为实施排查生成的**详细公开分析过程**：当前理解、待验证假设、依据、为什么选择这个工具、工具返回了什么、判断如何变化以及下一步。即使模型 API 返回 `reasoning_content`，也不直接把原始私有思维链原样展示；系统要求模型另行输出足够详细、可审计、可被数据库证据验证的分析记录。

## 二、六个现有问题及代码根因

### 2.1 回答“你是什么模型”后不能继续提问

现状：

- 模型返回 `RESPOND` 后，自主任务被写成 `COMPLETED`。
- 前端输入框只在 `WAITING_USER` 时出现。
- 后端 `RESPOND_AUTONOMOUS_QUESTION` 也只接受 `WAITING_USER` 状态。
- `COMPLETED`、`STOPPED` 和普通回答完成后均没有“继续发送消息”的动作。

涉及位置：

- `DiagnosisAutonomousRunner`：`RESPOND` 被当成终止动作。
- `DiagnosisCaseService.respondAutonomous()`：只允许回答模型正在等待的问题。
- `DiagnosisCasePanel.vue`：输入框只在 `WAITING_USER` 时渲染。

修正：

- 普通回答后进入 `READY`，不进入不可继续的 `COMPLETED`。
- 自主模式底部始终保留一个对话输入框；仅在取消、权限阻断等不可恢复状态禁用。
- 增加统一动作 `SEND_AUTONOMOUS_MESSAGE`：
  - `READY`：开始下一轮分析。
  - `WAITING_USER`：作为现场问题的回答继续分析。
  - `RUNNING`：立即显示用户消息并进入待处理队列，在当前工具边界结束后交给模型。
  - `STOPPED/FAILED`：保留旧证据并开始新一轮，不清空历史。
- 用户点击发送后，前端先乐观展示用户消息；接口失败时在该消息下显示失败原因，不能让消息直接消失。

### 2.2 “提供具体案例”含义不清，而且强制输入患者 ID

当前“案例”实际承担两个职责：

1. 告诉系统用户看到的异常范围。
2. 提供一条修改前后可以核对的验收样本。

但这两个职责并不总是需要患者 ID。例如：

- 骨伤一科没有统计到手术：排查对象是科室。
- 某月结果突然降低：排查对象是时间段。
- 排除 ICU 和留观病房：排查对象是业务范围。
- 整体分母比医院少：可以没有任何具体记录编号。

因此将“提供具体案例”改名为：

> 选择排查范围（具体记录可选）

标准模式根据当前指标动态显示可选范围：

| 排查范围 | 何时显示 | 需要填写 |
|---|---|---|
| 某条记录 | 当前指标能证明业务唯一键时 | 就诊号、事件号、医嘱号或手术号，可多条 |
| 某个科室/病区 | SQL 或字段字典中存在可追溯科室、病区字段时 | 科室名称或代码 |
| 某个时间段 | 当前口径存在可追溯统计时间字段时 | 开始、结束时间 |
| 某类数据 | 当前 SQL 存在可安全选择的状态、类型、标记字段时 | 字段、条件和值 |
| 整体结果 | 所有指标都支持 | 异常现象，不要求记录编号 |

后端新增 `DiagnosisScopeCapabilities`，从当前生效实体、字段字典和 SQL 血缘确定性返回：

```text
recordKeyCandidates[]
departmentCandidates[]
timeFieldCandidates[]
conditionFieldCandidates[]
supportsAggregateOnly
```

前端不能自己猜当前指标应该输入患者 ID、事件号还是科室。

### 2.3 “医院确认的业务规则”为什么必填

它当前有两个用途：

- 记录医院为什么提出这次修改，供审计和医院草稿说明使用。
- 帮助实施人员用大白话确认预期变化。

它本身不是 SQL 改写依据。真正改写 SQL 的依据是结构化字段、操作符和值，或者完整候选 SQL。

调整规则：

| 处理分支 | 是否显示 | 是否必填 |
|---|---:|---:|
| 原口径重新抽取/重新计算 | 不显示 | 否 |
| 只核对原因、不修改 SQL | 改为“补充说明” | 否 |
| 修改抽取 SQL | 改名为“医院希望怎样处理这些数据” | 是 |
| 修改统计 SQL | 改名为“医院希望怎样计算分子分母” | 是 |
| 保存医院草稿 | 显示为“本次修改说明” | 是 |

文案明确说明：

> 这段说明用于确认医院的业务要求和生成草稿说明；程序实际修改 SQL 时仍以已选择的字段、条件和值为准。

### 2.4 重新抽取后数据就恢复的场景

这类问题通常不是口径修改，而是：

- 上一次同步中断或未完成。
- 业务数据在正式计算后才补录。
- 中间表快照被旧批次覆盖。
- 事件数据刚刚重新生成。
- 相同 SQL 再执行时业务库已经有了新数据。

不能把它引导到“生成候选 SQL”或“保存医院草稿”。新增独立分支：

> 使用当前正式口径重新抽取并核对

推荐流程：

```text
保存当前正式批次结果和中间表摘要
  → 使用完全相同的正式抽取 SQL 写入影子表
  → 对比当前正式中间表与最新业务源结果
  → 若影子表补出了缺失记录，结论标记为“数据同步或快照未更新”
  → 实施人员明确点击“按原口径正式重新计算”
  → 复用现有正式抽取与计算链路
  → 对比重算前后分子、分母、结果和记录差异
```

规则：

- 第一次核对只写影子表，不清空正式中间表。
- 只有实施人员明确确认后，才调用现有正式计算链路。
- 正式重算必须使用医院执行锁、批次号和快照校验。
- 如果重算后恢复，任务可以按 `DATA_REFRESHED` 结束，不生成候选 SQL，也不保存医院草稿。
- 如果最新业务源仍缺数据，再进入业务数据缺失或 SQL 口径排查。

### 2.5 选择自主模式后仍出现标准模式内容

这是明确的前端条件错误，不是产品设计问题。

当前具体原因：

- “提供具体案例”已经有 `selectedMode === 'STANDARD'` 限制。
- 但后面的 `investigationReached` 整块没有限制 `investigationMode`。
- 自主工具执行后会产生 `evidence`，使 `investigationReached` 为真，于是标准模式的“请实施人员提供排查要求”“当前指标能自动修改什么”等内容被渲染出来。
- 通用证据循环还会把 `AUTONOMOUS_TOOL` 当成用户证据消息渲染；该证据没有标准模式的 `summary`，从而出现空白用户消息。

修正原则：

```text
STANDARD 分支：只渲染标准模式组件和标准证据类型。
AUTONOMOUS 分支：只渲染自主对话、Agent事件和自主候选/试跑结果。
```

具体要求：

- 选择方式之前，只显示两种方式的说明，不显示任何具体案例表单。
- 选择标准模式后才显示“选择排查范围”。
- 选择自主模式后只显示一个自由问题输入框。
- `investigationReached` 必须增加标准模式判断。
- 通用证据消息必须按证据类型白名单渲染；`AUTONOMOUS_TOOL` 只能进入自主过程时间线。
- 没有标题和正文的消息不得创建空白气泡。

### 2.6 自主模式展示不像对话，也没有阶段性回复

现状把 `ANALYSIS`、`TOOL_CALL`、`OBSERVATION` 全部平铺为同等级卡片，且模型的分析摘要在“公开分析”和“需要现场补充”中重复出现。

推荐改为“对话是主线，执行过程是附属证据”：

```text
实施人员消息（正常聊天气泡）

AI 阶段性回复（正常聊天正文，深色）
└─ 详细分析过程 · 3.2s                   [当前轮自动展开/可收起]
   ├─ 问题理解、候选原因和已有依据（浅色）
   ├─ 本轮验证目标和工具选择理由
   ├─ 调用：读取本次运行证据            [展开详情]
   ├─ 观察：取得分子10、分母417
   ├─ 判断更新
   └─ 调用：查询业务库                  [展开详情]

AI 阶段性回复（正常聊天正文，深色）
└─ 已分析 · 4.1s                         [展开]
   └─ ……

最终结论（独立结果卡）
```

## 三、自主模式的新对话协议

### 3.1 运行状态

```text
IDLE          尚未开始
RUNNING       模型或工具正在执行
WAITING_USER  缺少医院现场信息
READY         本轮已回复，可以继续追问
COMPLETED     用户明确结束排查或已保存最终结果
STOPPED       达到上限或人工停止，可以继续发起新一轮
FAILED        技术失败，保留证据后可重试
```

普通问题如“你是什么模型”回答后进入 `READY`，不能进入不可继续的 `COMPLETED`。

### 3.2 模型动作

在现有 `CALL_TOOL / ASK_USER / FINAL / RESPOND` 基础上增加：

```text
REPORT_PROGRESS
```

用途：模型已经形成一个对实施有价值的阶段性结论，但仍需继续查证时，先向用户发送一条正常回复，再继续循环。

动作语义：

| 动作 | 是否调用工具 | 是否结束本轮 |
|---|---:|---:|
| RESPOND | 否 | 本轮结束，状态 READY |
| REPORT_PROGRESS | 否 | 否，展示阶段性回复后继续 |
| CALL_TOOL | 是 | 否 |
| ASK_USER | 否 | 暂停并等待用户 |
| FINAL | 否 | 形成总结果，状态 READY；用户仍可追问 |

### 3.3 Hook 事件

吸收 Hook 结构，将显示和审计逻辑移出循环主体：

```text
UserMessageSubmit   用户消息已保存
BeforeModel         显示“思考中”并开始计时
AfterModel          保存详细公开分析字段和模型动作
PreToolUse          保存工具名称和输入参数
PostToolUse         保存结果摘要、耗时、错误和证据编号
StageReply          保存阶段性正常回复
Stop                保存最终结论或停止原因
```

推荐事件结构：

```json
{
  "seq": 12,
  "turnId": "TURN_xxx",
  "eventType": "PUBLIC_ANALYSIS | TOOL_STARTED | TOOL_FINISHED | STAGE_REPLY | ASK_USER | FINAL",
  "status": "RUNNING | SUCCEEDED | FAILED",
  "publicAnalysis": "下一步要核对骨伤一科手术记录在哪一层消失。",
  "tool": "query_indicator_data",
  "toolDisplayName": "查询指标数据",
  "arguments": {},
  "observation": "业务库12条，中间表0条。",
  "durationMs": 820,
  "evidenceId": "AEVD_xxx"
}
```

### 3.4 对话持久化

自主模式不能只保存一个 `problem` 和一个 `pendingQuestion`。调整为：

```text
autonomousRun
  status
  activeTurnId
  turns[]
    userMessage
    submittedAt
    processEvents[]
    stageReplies[]
    finalReply
  pendingUserMessages[]
  findings[]
  finalConclusion
```

刷新页面、切换对话后按 `caseId` 恢复完整对话和执行过程，不重新调用模型或工具。

### 3.5 消息接口

增加统一动作：

```text
SEND_AUTONOMOUS_MESSAGE
```

请求：

```json
{
  "message": "骨伤一科为什么没有统计到手术？",
  "clientMessageId": "MSG_CLIENT_xxx"
}
```

响应必须立即包含已保存的用户消息。前端使用 `clientMessageId` 去重，避免乐观消息和服务端消息重复。

现有增量事件接口继续使用：

```text
GET /api/diagnosis/cases/{caseId}/agent-events?afterSeq=...
```

第一阶段使用 500～800ms 增量轮询即可，不必为此引入 WebSocket。模型调用前先保存 `BeforeModel` 事件，页面才能及时显示“思考中”。

## 四、标准模式的新流程

### 4.1 页面顺序

```text
选择标准模式
  → 选择排查范围
  → 系统澄清当前口径和数据链路
  → 选择本次处理方式
      ① 使用原口径重新抽取并核对
      ② 修改抽取范围或条件
      ③ 修改分子分母统计逻辑
  → 执行对应验证
  → 结束排查或保存医院草稿
```

### 4.2 “选择排查范围”动态表单

示例一：患者入院48小时内转科的比例

```text
排查范围：某条记录 / 某个科室 / 某个时间段 / 整体结果
记录编号类型：就诊号
科室字段：当前科室、来源科室、目标科室
```

示例二：骨伤一科没有统计到手术

```text
排查范围：某个科室
科室：骨伤一科
具体患者或手术号：可选，用于进一步验收
```

示例三：整体分母偏低

```text
排查范围：整体结果
异常说明：医院认为同期应有约500人次，系统只有417人次
具体记录编号：不显示
```

### 4.3 SQL 修改表单

只有选择“修改抽取 SQL”或“修改统计 SQL”后才展示：

1. 医院希望怎样处理这些数据。
2. 判断字段、条件和值。
3. 现场核对 SQL（可选）。
4. 完整候选 SQL（程序无法安全改写时才显示）。

“当前指标能自动修改什么”属于标准模式的技术帮助，默认折叠，不得出现在自主模式对话中。

## 五、前端视觉与交互设计

### 5.1 页面唯一任务

面向医院实施人员，页面唯一任务是：

> 看清系统正在验证什么、拿到了什么证据、现在需要我做什么，以及最后是否找到原因。

### 5.2 视觉层级

不直接复制截图的深色终端主题，保持当前医院系统的浅色界面，但吸收其信息层级。

| 内容 | 视觉 | 作用 |
|---|---|---|
| 用户消息 | 现有浅蓝对话气泡 | 明确实施人员输入 |
| AI 阶段性回复 | 深色正文、正常对话宽度 | 用户首先阅读的内容 |
| 思考/公开分析 | `#F4F6FA` 浅灰蓝背景、`#667085` 辅助文字 | 可折叠的过程信息 |
| 工具执行 | `#F7F9FC` 背景、细边框、等宽工具名 | 像可点击的执行记录 |
| 工具成功观察 | `#EFF8F6` 淡绿背景、`#226C5B` | 说明获得了什么事实 |
| 工具失败 | `#FFF2F0` 淡红背景、`#B42318` | 说明失败点和下一步 |
| 最终结论 | `#EFF4FF` 背景、左侧深蓝强调线 | 一眼定位总结果 |

特色元素是“证据轨道”：同一轮中的分析、工具和观察通过一条细竖线连接，但正常 AI 回复和最终结论不放在线内，避免所有内容看起来都像日志。

### 5.3 “思考中”折叠块

执行中：

```text
◌ 思考中 · 3s                                  展开
```

完成后：

```text
✓ 已分析 · 3.2s                                展开
```

展开后显示：

- **当前问题理解**：模型怎样理解实施人员刚才的问题。
- **当前判断与候选原因**：列出正在验证的1～3个可能原因，并标记“待验证”，不能冒充结论。
- **已有依据**：引用知识库页、运行证据或上一轮工具证据编号。
- **本轮验证目标**：这一轮准备确认或排除什么。
- **工具选择理由**：为什么调用这个工具，而不是直接回答或调用另一个工具。
- **工具调用信息**：工具名称、数据库侧、查询对象、参数摘要；SQL在工具详情中完整展示。
- **工具观察结果**：实际返回数量、关键字段、错误和证据编号。
- **判断更新**：哪些候选原因被确认、排除或仍然缺证据。
- **下一步动作**：继续调用工具、询问实施人员，或形成阶段性/最终回复。

显示行为：

- 模型开始工作后，“思考中 · Ns”立即出现并**自动展开当前正在执行的一轮**，不需要用户反复点击。
- 新的分析或工具事件到达时在展开区内实时追加；页面不自动跳回顶部。
- 本轮完成后保持展开状态；用户可以点击收起，也可以再次点击查看完整过程。
- 多轮对话按轮次分组，默认只自动展开最新一轮，历史轮次保持用户上次的展开状态。
- 正常的阶段性回复仍显示在折叠块外，不能只在过程日志里出现。

前端标题使用“详细分析过程”，辅助说明为“展示模型主动输出的分析、工具依据和判断变化”。不显示模型原始私有思维链；这样既能让实施人员完整看懂排查路径，也不会把不可验证的内部 token 当成事实。

后端每个分析事件至少保存：

```text
turnId
sequence
problemUnderstanding
hypotheses[]
evidenceRefs[]
verificationGoal
toolChoiceReason
observationSummary
judgementUpdate
nextAction
createdAt
```

如果模型只返回“继续查询”之类没有依据的短句，本轮输出判为不合格，要求模型补齐上述公开分析字段后才允许调用工具。

### 5.4 工具条

默认只显示一行：

```text
▣ 查询指标数据 · 业务库 · 返回200行 · 260ms       查看
```

点击后显示：

- 工具中文名和技术名。
- 数据库侧。
- 实际 SQL 和参数。
- 返回行数和是否截断。
- 最多10行结果预览。
- 执行耗时。
- 错误摘要。
- 证据编号。

不显示数据库密码、连接串和认证令牌。

### 5.5 避免重复内容

- `ANALYSIS + ASK_USER` 合并为同一轮过程块；公开分析只显示一次。
- 提问正文作为正常 AI 消息显示，不再额外重复一遍“需要现场确认”。
- `TOOL_STARTED + TOOL_FINISHED` 在前端合并成一条可更新的工具条。
- 工具观察不再复述完整 JSON，只显示面向实施的事实摘要；JSON 放在展开详情。

## 七、真实浏览器验收标准

验收入口统一从真实浏览器打开 `http://127.0.0.1:8765/`，完成三步基础校验后执行。

### 7.1 自主模式连续对话

1. 选择“DeepSeek 自主排查”。
2. 页面此时不能出现“提供具体案例”“当前指标能自动修改什么”或标准 SQL 表单。
3. 输入“你是什么模型”。
4. 用户消息在点击发送后1秒内显示。
5. 页面显示“思考中”，随后显示直接回答。
6. 本轮工具调用数必须为0。
7. 回答完成后输入框仍存在且可继续发送。
8. 再输入“当前指标的分子分母是多少，证据在哪里”。
9. 新消息立即显示，旧回答不消失。
10. 页面出现公开分析、工具执行、观察和最终回复，不得卡在 `COMPLETED`。

### 7.2 自主过程视觉

1. 模型调用开始后1秒内出现“思考中 · Ns”。
2. 当前轮“思考中”自动展开；用户收起后可以再次点击展开。
3. 展开区必须依次看到问题理解、候选原因、已有依据、验证目标、工具选择理由、工具观察、判断更新和下一步，不能只有一句摘要。
4. 工具调用发生时，正在展开的分析区实时追加工具状态，不等整轮结束后一次性出现。
5. 工具条与正常 AI 回复颜色、字号和层级明显不同。
6. 点击工具条可看到工具输入、SQL、参数、耗时、返回数量和证据编号。
7. 工具结果超过10行时只预览10行，并明确提示已限制展示。
8. 阶段性回复以正常 AI 对话形式显示，不埋在工具日志中。
9. 最终结果使用独立结论卡，包含已确认事实、未确认事实和建议下一步。
10. 页面不得出现重复的分析内容、重复提问或空白消息气泡。
11. 历史轮次可分别展开，刷新页面后分析事件、工具事件和展开内容均可恢复。
12. 页面标注“详细分析过程（公开、可审计）”，不把模型 API 的原始私有思维链直接展示给用户。

### 7.3 自主模式现场追问

1. 输入“排除测试患者”。
2. 模型缺少医院定义时可以询问标识方式。
3. 实施回复“按科室排除”后，消息应立即显示。
4. 模型需要科室名称或代码时可以调用只读查询。
5. 查询获得科室列表后，先给出简短阶段性回复，再要求实施确认具体科室。
6. 全程不能出现标准模式的字段改写表单。
7. 刷新浏览器后，用户消息、阶段回复、工具过程和当前待回答问题全部恢复。

### 7.4 标准模式按指标动态输入

1. 重新创建排查任务，选择“标准模式”。
2. 只有此时才显示“选择排查范围”。
3. 对“患者入院48小时内转科的比例”，可选择具体记录、科室、时间段或整体结果。
4. 选择“某个科室”后，不要求患者 ID。
5. 选择“整体结果”后，不显示记录编号输入框。
6. 选择“某条记录”后，记录编号才成为必填。
7. 字段和范围名称优先显示中文名，技术字段作为辅助信息。

### 7.5 业务规则字段

1. 选择“原口径重新抽取并核对”时，不显示“医院确认的业务规则”。
2. 选择“只核对原因”时，补充说明为可选。
3. 选择“修改抽取 SQL”时，显示“医院希望怎样处理这些数据”并说明用途。
4. 未填写说明时不能保存医院草稿，但可以先执行只读核对。
5. 页面明确提示真正改写 SQL 以结构化字段、条件和值为准。

### 7.6 重新抽取恢复数据

准备一个业务库已有、正式中间表暂缺的测试批次：

1. 选择“使用当前正式口径重新抽取并核对”。
2. 系统先展示当前正式分子、分母、中间表行数和批次号。
3. 系统使用相同正式 SQL写入影子表，不修改正式表。
4. 页面展示影子表新增了哪些记录，以及候选分子分母变化。
5. 若影子结果恢复，结论显示“SQL 未变化，业务源或同步快照已更新”。
6. 页面提供“按原口径正式重新计算”，并明确会更新正式结果。
7. 实施确认后复用正式链路完成计算。
8. 重算后显示前后结果对比，任务状态为 `DATA_REFRESHED`。
9. 全程不生成候选 SQL，不出现“保存医院草稿”。

### 7.7 模式隔离和异常恢复

1. 自主模式不得渲染标准模式表单、标准证据用户气泡和空白消息。
2. 标准模式不得渲染自主 Agent 时间线。
3. 工具执行失败时，工具条显示失败原因和建议，不吞掉之前消息。
4. 人工停止后可以继续发消息重新开始一轮，旧证据保留。
5. 达到轮次或时间上限后显示停止原因，并允许继续排查。
6. 连续快速发送两条消息时，前端不丢消息、不重复消息；后端按顺序消费。

### 7.8 验收证据

每个浏览器场景保存：

- 页面完整截图。
- 展开“思考中”和工具详情后的截图。
- Network 中发送消息和增量事件请求。
- 对应 `caseId` 的结构化快照。
- Agent 事件序列及 `seq/turnId`。
- 工具调用次数和工具证据编号。
- 重新抽取场景的正式批次、影子批次和前后对账结果。

## 八、固定约束

- 模型不能直接修改正式 SQL、正式表或知识库。
- 私有思维链不展示；“思考中”自动展开模型专门输出的详细公开分析过程和可验证证据。
- 模型的阶段性回复不能冒充已验证事实。
- 工具输入、输出和错误必须可审计，但不显示密码、连接串和令牌。
- 自主模式与标准模式必须完全隔离，不能共享未加类型判断的渲染区块。
- 记录编号不是所有排查的必填项；是否需要由当前指标能力和排查范围决定。
- 重新抽取恢复数据不属于医院口径修改，不生成医院草稿。
- 正式重新计算必须由实施人员明确确认，并复用现有正式抽取、执行锁、批次和快照链路。
